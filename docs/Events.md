# Events

Watodo's calendar event system is built around recurring **event series**. A
series stores a recurrence rule (serialized with the
[rrule](https://github.com/jakubroztocil/rrule) library) and expands
occurrences on demand, so a series can repeat for many years without any
maintenance. Individual occurrences can be cancelled or rescheduled, and both
work role slots and comments can be attached to a whole series or to a single
occurrence.

## Data model

| Table | Purpose |
|-------|---------|
| `organizations` | Has a `default_timezone` (IANA name, default `UTC`). Series inherit it when no explicit timezone is set. |
| `calendars` | Belong to an organization; series live in a calendar. |
| `event_series` | A recurring event: title, description, calendar, start (timestamptz), duration (minutes), all-day flag, timezone, visibility, and the recurrence rule as a canonical `RRULE:` string (`rrule` column, null for one-off events). |
| `event_exceptions` | Per-occurrence overrides, keyed by `(event_series_id, occurrence_start)`: `is_cancelled` and/or `override_start` / `override_end` for rescheduling. |
| `event_work_roles` | Work role slots. `event_occurrence_id` is null for series-wide slots or references a materialized occurrence (`event_occurrences.id`) for occurrence-specific slots. |
| `event_work_role_assignments` | Users assigned to a work role slot (unique per slot + user). |
| `event_comments` | Comments. `occurrence_start` is null for series-wide comments or an occurrence start for occurrence-specific comments. |

The first user to log in is bootstrapped with a default organization (with its
`default_timezone`), an admin role, and a default calendar.

## Timezones

Each series has a timezone: the explicitly configured one, or the
`default_timezone` of the organization that owns its calendar.

Recurrence rules are evaluated in the series' timezone using **wall-clock
mode**: the rrule library works with dates whose UTC components are the
wall-clock time in the series timezone, and `date-fns-tz` converts between
those and real UTC instants. This keeps occurrence times stable across DST
transitions and independent of the server's process timezone (rrule's own
`tzid` option is process-timezone-dependent, so it is not used). A weekly
meeting at 10:00 stays at 10:00 local time all year; the UTC instant shifts
with DST.

## Recurrence rules

The API accepts a structured recurrence object and serializes it to a canonical
RRULE string at write time:

| Field | Frequencies | Meaning |
|-------|-------------|---------|
| `freq` | all | `DAILY`, `WEEKLY`, `MONTHLY` or `YEARLY` (required). |
| `interval` | all | Repeat every N units (default 1, max 366). |
| `byWeekdays` | `DAILY`, `WEEKLY` | ISO weekdays, 1 = Monday .. 7 = Sunday. Weekly defaults to the weekday of the start; for daily rules it acts as a filter (e.g. weekdays only). |
| `byMonthDays` | `MONTHLY` | Days of the month (1-31). Defaults to the day of the start. |
| `until` | all | End date as an ISO instant. |
| `count` | all | Maximum number of occurrences. |

Example: `{ "freq": "WEEKLY", "byWeekdays": [1, 3], "until": "2027-01-01T00:00:00.000Z" }`
is stored as `RRULE:FREQ=WEEKLY;BYDAY=MO,WE;UNTIL=...`.

Occurrences are **expanded on demand** with `rule.between()` over the requested
time window; nothing is stored per occurrence. A series can therefore repeat
for 5-10 years or more without maintenance. Range queries are capped at about
10 years (`MAX_OCCURRENCE_RANGE_MS`, 3700 days) and return 400 beyond that.

## Occurrences and exceptions

An occurrence is identified by its **original start instant** (the occurrence
start as generated by the rule, before any override). This identity is used
for exceptions, work role slots, and comments.

- **Cancel** creates/updates an exception with `is_cancelled = true`. Cancelled
  occurrences are hidden from range expansions and marked in occurrence
  details.
- **Reschedule** creates/updates an exception with `override_start` (and
  `override_end`, defaulting to the new start plus the series duration). The
  occurrence appears at its new time and is flagged `isRescheduled`. Its
  original slot is freed.
- **Restore** deletes the exception, returning the occurrence to its original
  position.

Expansion applies exceptions in two passes: occurrences inside the window are
filtered/overridden directly, and exceptions whose original occurrence fell
outside the window but whose override lands inside it are swept in, so
rescheduled occurrences appear even when the original slot is far outside the
queried range.

Operations on a specific occurrence validate that the given instant is really
an occurrence of the series and return 404 otherwise.

Changing a series' start, recurrence rule, or timezone invalidates all of its
exceptions, so updating any of those clears `event_exceptions` for the series.

## Splitting a series (edit this and all following)

`POST /api/v1/event-series/:seriesId/occurrences/:occurrenceStart/split`
implements "edit this and all following": the edited occurrence begins a
**new, independent series** with the given parameters, and the original series
is truncated so it ends just before the split occurrence. The body is the same
as a series update (all fields optional); fields that are not provided are
inherited from the original series, and `start` defaults to the split
occurrence. The response is the new (or updated) series.

The consequences, which the UI spells out before the action is carried out:

- All exceptions (cancellations and reschedules) of the original series from
  the split occurrence onwards are **reset**. Exceptions before the split
  point are kept.
- The original series and the new series are fully independent. Later edits
  to the original series do not cascade to the new series, and vice versa.
- Work role slots and comments are not copied to the new series. Series-wide slots
  and comments remain on the original series; occurrence-specific ones stay
  keyed to the original series and do not show up on the new series.

When the recurrence is inherited and the new start is not an occurrence of the
rule (for example moving a Monday+Wednesday series so it starts on a
Thursday), the start's weekday (`WEEKLY`, or `DAILY` with `byWeekdays`) or day
of month (`MONTHLY` with `byMonthDays`) is added to the rule, so the new start
is always an occurrence of the new series. When an explicit recurrence is
given, the start must be an occurrence of it, otherwise the request fails
with 400.

Splitting at the **first** occurrence of a series (or splitting a one-off
series) updates the series in place instead: it keeps its id and all of its
exceptions are reset. This avoids leaving behind an empty series and keeps
series-wide work role slots and comments attached to the series.

Splitting at an instant that is not an occurrence of the series returns 404.

## Work role slots

Work role slots describe responsibilities attached to an event. A slot is either
**series-wide** (`occurrenceStart` null, applies to every occurrence) or
**occurrence-specific** (tied to one occurrence start). Users are assigned to
slots via `event_work_role_assignments`; assigning the same user twice returns 400.
Assignments and slots are deleted with the series (cascade).

## Comments

Comments work like work role slots: series-wide (`occurrenceStart` null) or scoped to
one occurrence. Any user with `events:write` can add a comment; only the author
can edit or delete their own comments (403 otherwise).

## Permissions

| Permission | Allows |
|------------|--------|
| `events:read` | Listing series, calendars, and reading occurrences, exceptions, work role slots, and comments. |
| `events:write` | Creating/updating/deleting series, calendars, cancelling/rescheduling/restoring occurrences, managing work role slots and assignments, and managing comments. |

The `admin` permission bypasses all checks.

## API reference

All endpoints are under `/api/v1`. Mutations require the `x-token` header.
Responses use camelCase. `occurrenceStart` path parameters are ISO 8601
instants (URL-encoded).

### Organizations and calendars

| Method | Path | Permission | Description |
|--------|------|------------|-------------|
| GET | `/organizations` | authenticated | Organizations the current user belongs to (with `defaultTimezone`). |
| GET | `/calendars` | `events:read` | List calendars. |
| POST | `/calendars` | `events:write` | Create a calendar: `{ name, organizationId, googleCalendarId? }`. |

### Event series

| Method | Path | Permission | Description |
|--------|------|------------|-------------|
| GET | `/event-series?calendarId=` | `events:read` | List series (optionally filtered by calendar). |
| POST | `/event-series` | `events:write` | Create a series (see below). |
| GET | `/event-series/occurrences?start=&end=&calendarId=` | `events:read` | Occurrences of all visible series in a time range. |
| GET | `/event-series/:seriesId` | `events:read` | Get one series. |
| PATCH | `/event-series/:seriesId` | `events:write` | Update a series (all fields optional). |
| DELETE | `/event-series/:seriesId` | `events:write` | Delete a series (cascades work role slots, assignments, comments, exceptions). |

Create/update body:

```json
{
  "title": "Weekly sync",
  "description": "Team sync",
  "calendarId": "22222222-2222-4222-8222-222222222222",
  "start": "2026-10-26T10:00:00.000Z",
  "durationMinutes": 90,
  "isAllDay": false,
  "timezone": "Europe/Helsinki",
  "isVisible": true,
  "recurrence": { "freq": "WEEKLY", "byWeekdays": [1, 3] }
}
```

`timezone` and `recurrence` are optional; the timezone defaults to the
organization's `defaultTimezone`. `recurrence: null` removes the rule.

### Occurrences of one series

| Method | Path | Permission | Description |
|--------|------|------------|-------------|
| GET | `/event-series/:seriesId/occurrences?start=&end=` | `events:read` | Occurrences of one series in a time range. |
| GET | `/event-series/:seriesId/occurrences/:occurrenceStart` | `events:read` | Occurrence detail: series, occurrence, workRoles (series-wide + occurrence-level), comments (series-wide + occurrence). |
| POST | `/event-series/:seriesId/occurrences/:occurrenceStart/cancel` | `events:write` | Cancel this occurrence. |
| POST | `/event-series/:seriesId/occurrences/:occurrenceStart/reschedule` | `events:write` | Reschedule: `{ start, end? }`. |
| POST | `/event-series/:seriesId/occurrences/:occurrenceStart/split` | `events:write` | Edit this and all following occurrences: starts a new series at this occurrence (see "Splitting a series"). |
| DELETE | `/event-series/:seriesId/occurrences/:occurrenceStart/exception` | `events:write` | Remove the exception (restore the occurrence). |
| GET | `/event-series/:seriesId/exceptions` | `events:read` | List all exceptions of a series. |

An expanded occurrence looks like:

```json
{
  "seriesId": 1,
  "title": "Weekly sync",
  "description": "Team sync",
  "isAllDay": false,
  "occurrenceStart": "2026-11-02T10:00:00.000Z",
  "start": "2026-11-03T14:00:00.000Z",
  "end": "2026-11-03T15:30:00.000Z",
  "isRescheduled": true,
  "isCancelled": false,
  "exceptionId": 4
}
```

## Frontend

- **Calendar (Home)**: loads occurrences for the visible calendar range
  (padded by a day on each side) and renders them. Cancelled occurrences are
  hidden; rescheduled ones are marked. Clicking an occurrence opens a detail
  dialog.
- **Occurrence dialog**: shows the occurrence time, cancellation/reschedule
  notices, and the recurrence summary, plus work role slots (create, assign users,
  unassign, delete) and comments (add, edit/delete own). Occurrence actions:
  cancel, restore, reschedule to a new date/time, and "Edit this and all
  following", which opens the series dialog in split mode with a warning
  explaining that a new independent series is created, the original series is
  truncated, and future exceptions are reset. All write actions are shown only
  to users with `events:write` (or `admin`).
- **Events page (`/events`)**: manages series in a table (title, calendar,
  start, duration, recurrence summary) with create/edit/delete. The edit
  dialog contains the recurrence form (frequency, interval, weekdays, days of
  month, until, occurrence count) and a timezone field that defaults to the
  organization's `defaultTimezone`. When no calendar exists yet, the page
  offers to create one.

## Limits and caveats

- Occurrence range queries are capped at about 10 years; larger ranges return
  400.
- Changing a series' start, recurrence rule, or timezone deletes its
  exceptions (they are keyed by the original occurrence start).
- Recurrence evaluation happens in the series' timezone (wall-clock mode);
  moving a series to another timezone reinterprets its wall-clock times.
- `durationMinutes` must be positive (max 43200, i.e. 30 days).
